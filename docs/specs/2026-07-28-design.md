# StripGauge — design

2026-07-28

## Problem

The Touch Bar on a MacBook Pro shows nothing useful most of the time, while the number worth
watching during a working day — how much of the Claude subscription quota is gone — is only
visible by typing `/usage` inside Claude Code.

Goals: show it persistently, only while Claude Code is running, with no dependency on any
third-party app or CLI, and keep the whole thing small enough to read in one sitting.

## Where the numbers come from

Claude Code's `statusLine` hook runs any command and passes a JSON payload on stdin. That payload
already carries what is needed:

| Field | Meaning |
| --- | --- |
| `rate_limits.five_hour.used_percentage` | percentage of the 5-hour window consumed |
| `rate_limits.seven_day.used_percentage` | percentage of the 7-day window consumed |
| `context_window.used_percentage` | context used in the current session |

Two alternatives were rejected. Parsing `~/.claude/projects/**/*.jsonl` (what `ccusage` does)
yields consumption, not quota, and adds a dependency. Calling `api.anthropic.com/api/oauth/usage`
returns the authoritative window state but is undocumented, needs OAuth credentials and a spoofed
`User-Agent`, and is aggressively rate-limited.

The hook is also the reason no "is Claude Code running?" check is needed: nothing writes when
nothing is running.

Caveats that shape the code: `rate_limits` appears only for Claude.ai subscribers, only after a
session's first API response, and either window can be absent on its own.

## Shape

```
Claude Code ──JSON via stdin──▶ stripgauge statusline
                                      │ atomic write
                                      ▼
                     ~/Library/Application Support/stripgauge/state.json
                                      │ polled every 2s
                                      ▼
                              StripGauge.app (LSUIElement)
                                      │ DFRFoundation, via dlsym
                                      ▼
                             Control Strip on the Touch Bar
```

One binary, two modes, selected by argv. The two processes share only the state file, whose schema
is three fields: two optional percentages and a timestamp.

| Unit | Responsibility |
| --- | --- |
| `StripGaugeCore/Statusline.swift` | decode the subset of Claude Code's payload that matters |
| `StripGaugeCore/GaugeState.swift` | the shared contract: schema, atomic storage, staleness, merge |
| `StripGaugeCore/Label.swift` | text and severity, pure functions |
| `stripgauge/main.swift` | argv dispatch and the statusline path |
| `stripgauge/Gauge.swift` | AppKit lifecycle, polling, show/hide |
| `stripgauge/ControlStrip.swift` | the only file that touches private API |

`StripGaugeCore` never imports AppKit, which is what makes the logic testable on a machine with no
Touch Bar.

## Decisions and why

**Polling, not watching.** The state file is replaced by an atomic rename, which swaps the inode
and silently kills an fd-based watch. A 2-second timer is both simpler and correct.

**Staleness, not a liveness check.** The item hides when the file has not been written for 30
seconds. This requires `refreshInterval: 10` in the status line config, because status line
updates are event-driven and a session left idle stops emitting them.

**Merge instead of overwrite.** A session that reports no rate limits refreshes the timestamp but
keeps the percentages already on disk. Without this, opening a second session blanks the gauge
until that session makes its first API call. A stale previous state contributes nothing.

**Last writer wins across sessions.** Correct by construction: these percentages are account-wide,
so concurrent sessions all write the same values.

**The statusline mode never fails loudly.** Unreadable input leaves the last good state alone and
prints placeholders; the exit code is always 0, because a failure there would break the user's
status line in every session.

## What the Control Strip actually allows

Measured on macOS 26.5.2, M1 13-inch:

| Attempt | Result |
| --- | --- |
| explicit `widthAnchor` of 220 pt | discarded; granted 55.5 × 30 |
| content-sized, 121.5 pt of text | granted 319 pt, then not drawn at all |
| content-sized, 52 pt of text | granted 55.5 × 30, drawn correctly |

So the usable slot is about 55 × 30 pt: two rows of roughly six characters at 10 pt. `5h 100%`
measures 50 pt, so the worst case still fits. This is why the layout is two rows rather than one
line, and why no width constraint appears in the code.

The empty left half of the Touch Bar is not available. It is the app-specific region, owned by
whichever application is frontmost, and the Control Strip API offers no way to reach into it. The
only mechanism that owns the whole bar is `presentSystemModalFunctionBar`, which would also
displace the system brightness and volume buttons and would have to reimplement them — rejected.

## Testing

`swift test` covers payload decoding including every absent-field case, unknown fields, state
round-trip, the merge rules, label formatting, the worst-case row width, and the severity
thresholds. The private-API layer is verified by eye: ⇧⌘6 writes a Touch Bar screenshot.

## Out of scope for v1

Tap to cycle between quota, context, and cost. A countdown to the window reset. A launchd job for
auto-start — a Login Item covers it.
